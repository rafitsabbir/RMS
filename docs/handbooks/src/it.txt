# RMS Technical Operations Guide
@ Recruitment Management System — technology stack, architecture, production requirements, sizing, deployment and security
@ Describes the version on the dev branch as of 2 October 2026 (roles plan, Phase 2; not yet released). Contains no hostnames, passwords or connection strings.

## 1. At a glance
|Item|Value|
|---|---|
|Application type|Java web application packaged as a WAR file, deployed to Apache Tomcat (no embedded server)|
|Runtime|Java 21 or later, Tomcat 11 (Servlet 6.1, Jakarta EE 11)|
|Database|MySQL (5.7 or 8.x) through a Tomcat JNDI connection pool|
|Integrations|None: no e-mail, message queues, external APIs or batch jobs|
|Users' browsers|Load Bootstrap, jQuery and DataTables from the public CDN cdn.jsdelivr.net|

RMS is a single, stateful web application with one MySQL database.

## 3. Architecture
### Deployment view
![Deployment view: browser, proxy, Tomcat with the RMS WAR and connection pool, MySQL](it-deploy.png)

### Inside the application
![Request path through the application layers](it-inside.png)

- **Layers:** controller → service → DAO (data access) → model. All SQL lives in the DAO classes. No stored procedures, no ORM, no caching layer.
- **State:** the logged-in user is kept in the server-side HTTP session (cookie JSESSIONID). Sessions are not shared between servers.
- **Database tables:** users, admin (profiles and roles), position, language, candidate, marks.
- **No outbound calls** from the server except to MySQL.

## 5. Recommended hardware
> **These are estimates, not measurements.** No load test has been run. RMS is a small internal tool: a few simple SQL queries per page, no background jobs, and candidate documents (PDF, JPG, PNG up to 5 MB) stored as files. The figures assume up to about 50 users working at the same time; confirm with a load test if you expect more.

|Setup|vCPU|RAM|Disk|Java heap|
|---|---|---|---|---|
|**Application server only** (MySQL elsewhere) — recommended|2|4 GB|20 GB|-Xms512m -Xmx1g|
|Application and MySQL on one server|4|8 GB|50 GB SSD|-Xms512m -Xmx1g|
|Minimum (test or demo)|1|2 GB|10 GB|-Xmx512m|
|MySQL server (if separate)|2|4 GB|20 GB SSD plus backups|—|

- Disk is used mostly by logs, Tomcat and the JDK; the database itself is small (text rows only).
- **Document storage (RMS_DOC_DIR):** plan with about 6 files of up to 2 MB per candidate (12 MB; the hard limit is 5 MB per file). For example 1,000 candidates a year need about 12 GB a year, more if replaced documents aren't purged. Watch the free space; files are only removed by a Super Admin's permanent delete.
- The connection pool uses Tomcat's defaults (8 connections). Raise maxTotal in the context file if requests wait for connections under load.
- For high availability, two Tomcat nodes need sticky sessions at the load balancer, because sessions aren't replicated. Candidate ID generation is protected only within one node, so a database key on candidate.candidateid is advised before running two nodes.

## 6. Deployment
### Build
```
git checkout dev
./mvnw -B verify          (Windows: mvnw.cmd -B verify)
Result: target/rmsv2-1.0.1-SNAPSHOT.war
```
CI builds the same WAR on every push to the dev and master branches; it can be downloaded from the GitHub Actions run as "rms-war".

### First installation
1. Install JDK 21 and Tomcat 11. Copy mysql-connector-j-8.2.0.jar into Tomcat's lib/ folder.
2. Run db/migrations/001-candidate-isactive.sql, then 002-user-roles.sql, then 004-candidate-documents-jobs.sql, on the RMS database (once each). Check them against the real tables first (SHOW CREATE TABLE candidate, users and admin). Create the document folder (outside webapps), owned by the Tomcat user, and add RMS_DOC_DIR to the environment variables of step 5. Do not run 003-hash-passwords without the owner's approval.
3. Copy deploy/tomcat/rms.xml from the repository, unchanged, to conf/Catalina/localhost/rms.xml. It defines the jdbc/springrms connection pool with placeholders only.
4. Make Tomcat read the placeholders from the environment: add -Dorg.apache.tomcat.util.digester.PROPERTY_SOURCE=org.apache.tomcat.util.digester.EnvironmentPropertySource to CATALINA_OPTS (for example in bin/setenv.sh).
5. Provide the four environment variables listed in section 7, through the service manager or a file only the Tomcat user can read.
6. Deploy the WAR as webapps/rms.war (context path /rms), start Tomcat, and open /rms/login.

### Upgrade and rollback
- Run any new script in db/migrations/ first, then replace the WAR and restart Tomcat. Users must log in again after a restart.
- Keep the previous WAR. Rollback means redeploying it; undo a database migration only with the rollback statement in that script.
- A detailed, rehearsed runbook exists for the Phase 1 release (docs/release-phase1.md in the repository); the runbook for this version is still to be written.

## 7. Configuration
The application has no properties files and no profiles. All environment-specific settings live in Tomcat: the database connection and, since Phase 2, the document folder.

|Setting|Where|Purpose|
|---|---|---|
|RMS_DB_URL|Tomcat environment|JDBC URL of the RMS database; include sslMode=REQUIRED|
|RMS_DB_USER|Tomcat environment|Database account|
|RMS_DB_PASSWORD|Tomcat environment (protected)|Database password; never on the command line or in the repository|
|RMS_DOC_DIR|Tomcat environment|Absolute path of the folder for candidate documents (outside webapps). Read once at startup; unset or unusable means an ERROR in the log and no uploads or downloads|
|Upload limits|Inside the WAR (5 MB per file, 6 MB per request)|Tomcat's connector swallows at most 2 MB of a refused upload (maxSwallowSize); raise it (for example 10 MB) so users see "The file is larger than 5 MB" instead of a reset connection. The container's temporary folder holds uploads briefly: treat it as personal data|
|JNDI name jdbc/springrms|conf/Catalina/localhost/rms.xml|Connection pool the application looks up; validation query SELECT 1|
|Session timeout|Tomcat conf/web.xml (default 30 minutes)|RMS sets none of its own|
|Session persistence|Tomcat Manager element (off by default)|If enabled, user profiles are written to Tomcat's work/ folder: treat that folder as personal data|
|Logging levels|logback.xml inside the WAR|rms at INFO, Spring at WARN; console output|

> **A missing environment variable isn't reported at startup.** Tomcat leaves the placeholder text in place; the first login then fails with HTTP 500 and "Access denied" in the log.

## 8. Security
### In place
- Every page except the login page requires a login, and each page is open only to the roles listed for it; anything not listed is refused (Spring Security, four roles).
- Inactive users can't sign in and are signed out at their next click; role changes apply at once.
- New, reset and changed passwords are stored as bcrypt hashes; at least 8 characters.
- 5 failed logins for a username from one address in 15 minutes lock it there for 15 minutes.
- CSRF tokens protect every form; logout is a POST request.
- The session id changes at login; sessions use cookies only (HttpOnly, SameSite=Lax), never URLs.
- Response headers: X-Content-Type-Options nosniff, X-Frame-Options DENY, no caching of logged-in pages, and HSTS on HTTPS requests.
- All output is HTML-escaped; all SQL uses bound parameters.
- Uploaded documents: PDF, JPG or PNG only, at most 5 MB, checked by name, declared type and content (first bytes); stored outside the web root under random names; served only through the application, as downloads, to staff roles. Logs carry only document keys, user keys and counts.
- Log lines can't be forged by user input (line breaks are replaced).
- Dependency vulnerability scanning (OSV-Scanner) runs in CI.

### Open items for IT and security
|Item|Risk|Recommendation|
|---|---|---|
|Existing passwords are still plain text in users.password (new ones are bcrypt)|Critical|Run db/migrations/003-hash-passwords (a Java program; see its README). The column must hold at least 68 characters. Needs owner sign-off; afterwards older WARs (before Spring Security) can't log anyone in.|
|The login lock is in memory, per Tomcat node, by client address|Medium|Behind a reverse proxy, configure Tomcat's RemoteIpValve so the real client address is used; otherwise one user's failures lock that username for everyone. A restart clears the counts.|
|The session cookie isn't marked Secure|Medium|Serve only over HTTPS and mark the cookie secure (Tomcat or proxy).|
|HSTS includes subdomains|Check|Confirm this suits the production hostname.|
|The production version (master branch) is old: Spring 4.3, Connector/J 5.1.36|High|GitHub reports 26 security alerts on master. Release the upgraded version.|
|User ids appear in WARN log lines (refused requests)|Low|Restrict log access if user ids are personal data.|
|Uploaded files aren't virus-scanned|Medium|Scan RMS_DOC_DIR with the organisation's scanner (on access or scheduled). RMS checks only the file type.|
|Document folder access|Medium|Only the Tomcat user should read RMS_DOC_DIR; never serve it from a web server. It holds candidates' personal documents.|

## 9. Operations
- **Logs:** written to standard output, so Tomcat captures them in catalina.out (or the service journal). Set up log rotation. Watch for WARN lines from "rms." (refused access, duplicate users) and ERROR lines (database problems).
- **Health check:** there is no dedicated endpoint. GET /rms/login returning HTTP 200 shows that Tomcat and the application are up; it doesn't touch the database.
- **Backups:** back up the MySQL database **and** the RMS_DOC_DIR folder together, at the same point in time, and restore them together: a document row without its file gives "not found", and a file without its row is never found again. Apart from that folder the application server holds no data.
- **Restarts** log everyone out (sessions aren't persisted by default).
- **User administration** is done by a Super Admin on the Users and Roles screen (see the Business Analyst Guide, section 4). If the last Super Admin is locked out, the owner must fix it in the database.
- **Documents:** RMS never deletes files by itself. A Super Admin's "Permanently delete documents" removes a candidate's files and logs only the candidate key, the user key and the count. A startup ERROR "RMS_DOC_DIR is not set" means uploads and downloads are off.
- **Character set:** forms post ISO-8859-1. Keep WEB-INF/web.xml as shipped; without it Tomcat 11 rejects accented input with HTTP 400.

## 11. Decisions needed from IT
1. Which MySQL version runs in production? It decides whether the driver can move past 8.2.0.
2. The JDK standard: 21, or an organisational 17 or 25. The build can target 17 with a one-line change.
3. Who owns the Tomcat server, the JNDI configuration and the runtime? Is a Java Security Manager in use (Tomcat 11 doesn't support it)?
4. The deployment target: a virtual machine with Tomcat as described, or a container image (planned, not built yet).
. Where should RMS_DOC_DIR live (local disk or a network share), how is it backed up together with the database, and is a virus scanner available for it?
7. Should Tomcat's maxSwallowSize be raised so very large uploads get a clear message?
