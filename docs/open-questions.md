21. **Names stored as codes or control characters (G34):** the ISO-8859-1 forms store characters outside windows-1252 as `&#NNNN;` codes. This includes Cyrillic, Bengali and Latin letters such as ł and č. They store €, š, dashes and curly quotes as control characters U+0080–U+009F.
    - **What changed:** since the G27 fix (2026-09-30) the lists show the codes instead of the letters. The control characters still display as before.
    - **Question:** do any production position or language names contain either kind? Read-only checks for the owner:
      - `SELECT positionkey FROM position WHERE positionname LIKE '%&#%'`, for the codes.
      - `SELECT positionkey FROM position WHERE positionname REGEXP '[\\x{0080}-\\x{009F}]'`, for the control characters. This was tested on MySQL 8.0.46; MySQL 5.7's REGEXP may not accept it (#16).
      - The same queries on `language` (`languagekey`, `languagename`).
    - **If any exist:** fixing G34 needs a one-off conversion of those rows.
    - **Names entered outside the forms:** candidate and user names aren't entered through RMS forms, so they show exactly as stored. Do any of them contain intended markup or entities such as `&amp;`? Those now show literally.
22. **MySQL collation (G14, G17):** the duplicate check and the reactivation lookup compare names with `=` (`PositionDaoImpl.java:25-27`, `LanguageDaoImpl.java:27-29`), so an accent- or case-insensitive collation also matches "Café" and "CAFE", and reactivation then stores the typed spelling over the old one. Names are upper-cased in code, which doesn't remove accents. Which collation does the production `position.positionname` and `language.languagename` column use? Only `db/local` is confirmed here: `utf8mb4_unicode_ci` (`db/local/00-create-database.sql:9`, `docker-compose.yml:13`), which is accent- and case-insensitive. The Testcontainers DAO tests run on `mysql:8.0` and the repo sets no collation for them (`MySqlContainerSupport.java:48`), so they say nothing about production.
23. **NULL `isactive` (G17):** can `position.isactive` or `language.isactive` be NULL in production? A NULL row isn't listed (`isactive=1`), isn't counted by the duplicate check and isn't reactivated (`isactive=0`), so adding its name creates a second row. `db/schema.sql:40,47` is `NOT NULL DEFAULT 1`, but it's inferred (#19).
24. **Renaming onto a deleted name (G17):** should it stay allowed? Today the update check counts active rows only, so renaming onto the name of a deleted row succeeds and leaves a deleted and an active row with that name; if the active one is deleted later, adding the name reactivates the one with the lowest key (`PositionDaoImpl.java:26-27`, `LanguageDaoImpl.java:28-29`; tests `renameOntoTheNameOfADeletedPositionIsAllowed` and the language equivalent). The alternatives are refusing it or reactivating the deleted row. A `UNIQUE` index on the name (G33) would refuse it as well.
25. **Login behaviour after Spring Security (G13, 2026-10-01):** the password used to be compared in SQL; Spring Security now compares it in Java (`SecurityConfig.passwordEncoder`, `PlainTextPasswordEncoder`). Read-only checks for the owner:
    - **Case and trailing spaces:** the SQL comparison followed the `users.password` column's collation. On the MySQL defaults that ignores case (and, with PAD SPACE collations, trailing spaces), so "Secret" may have matched "secret". Now only the exact password works. Does anyone rely on that? The collation is in `SHOW FULL COLUMNS FROM users`.
    - **Duplicate usernames:** with no known unique index on `users.username` (G22), two rows could share one; each row's password used to work. Now such a username can't log in, with a WARN naming the userids. Check: `SELECT username, COUNT(*) FROM users GROUP BY username HAVING COUNT(*) > 1`.
    - **Empty passwords:** an empty stored password used to match an empty field; now it never matches. Check: `SELECT COUNT(*) FROM users WHERE password = '' OR password IS NULL`.
    - **Brace prefixes:** a stored plain-text password that starts with `{bcrypt}` would now be read as a hash. Check: `SELECT COUNT(*) FROM users WHERE password LIKE '{%'`.
    - **Migration (G13):** when should the stored passwords become `{bcrypt}` hashes? It needs a `password` column of at least 68 characters (`{bcrypt}` plus 60), and a rollback to an older WAR can't read hashed rows.
